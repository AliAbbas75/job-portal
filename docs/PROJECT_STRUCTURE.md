# Project Structure and Repo Hygiene

This is the reference for **where code goes and how files are named**. Every team member and every coding agent follows it. If something doesn't fit, raise it in a task rather than inventing a new location.

## 2. Where does it go?

| I'm writing... | Put it in | Example |
|---|---|---|
| A database table / entity | `backend/app/models/<entity>.py` | `models/job.py` → `Job`, `JobRequirement` |
| Request validation or JSON output shape | `backend/app/schemas/<entity>_schema.py` | `schemas/job_schema.py` → `JobSchema` |
| A candidate or public API endpoint | `backend/app/controllers/<resource>_controller.py` | `controllers/job_controller.py` → `job_bp` |
| A staff/admin API endpoint | `backend/app/controllers/admin/<resource>_controller.py` | `controllers/admin/approval_controller.py` |
| A business rule, multi-step operation, or anything touching >1 model | `backend/app/services/<area>_service.py` | `services/eligibility_service.py` |
| Something that runs on a timer | `backend/app/scheduler/<job>.py` (calls a service) | `scheduler/auto_close.py` |
| A tiny generic helper with no domain knowledge | `backend/app/utils/<topic>.py` | `utils/dates.py` |
| Email/SMS/PDF template | `backend/app/templates/<kind>/` | `templates/pdf/admit_card.html` |
| Seed or maintenance script | `backend/scripts/` | `scripts/seed_reference_data.py` |
| Backend test | `backend/tests/<layer>/test_<module>.py` | `tests/services/test_eligibility_service.py` |
| A call to the backend from React | `frontend/src/api/<resource>.js` | `api/jobs.js` → `getJobs()`, `getJob(id)` |
| A full screen reached by a URL | `frontend/src/pages/<audience>/<Name>Page.jsx` | `pages/public/JobDetailsPage.jsx` |
| A piece of UI used on 2+ pages | `frontend/src/components/<group>/<Name>.jsx` | `components/forms/CnicInput.jsx` |
| UI used by only one page | A folder next to that page | `pages/candidate/ProfilePage/EducationSection.jsx` |
| Stateful logic reused by components | `frontend/src/hooks/use<Name>.js` | `hooks/useApplicationCheck.js` |
| User-facing text | `frontend/src/i18n/en.json` (and `ur.json` once Urdu is in scope) | `"jobs.apply": "Apply"` |
| Styles for a component or page | Tailwind classes in its JSX; shared tokens/utilities only in `frontend/src/index.css` | `className="rounded-md bg-surface p-4"` |
| A dropdown of any kind | `components/forms/Select` / `SelectField` (4 visible items, scrolls) | `<SelectField label=… options=… />` |
| Mock response for an endpoint not built yet | `frontend/src/api/mocks/<resource>Mock.js` | `api/mocks/jobsMock.js` |
| Product/tech documentation | `docs/` | `docs/decisions.md` |
| Task status, milestones, work logs | `workspace/` | |

When a page grows its own sub-components, turn it into a folder:

```
pages/candidate/ProfilePage/
├── index.jsx              # the page (export default)
├── EducationSection.jsx
└── ExperienceSection.jsx
```

## 3. MVC layer rules

```
React page → src/api/* → controller → service → model → PostgreSQL
                          ↑ schema validates input / serializes output
```

| Layer | May import | Must NOT |
|---|---|---|
| `models/` | `extensions` (db), other models | import controllers, services, schemas; contain request handling |
| `schemas/` | models, marshmallow | query the database, hold business rules |
| `services/` | models, other services, utils | touch `flask.request`, return HTTP responses |
| `controllers/` | services, schemas, auth decorators | run queries directly, contain business rules |
| `scheduler/` | services | contain business rules itself |
| `utils/` | standard library only | import from any app layer |
| React components | hooks, api modules, other components | call Axios directly, hard-code user-facing text or colours |
| `api/mocks/` | reference data, other mocks | be imported by anything outside `src/api/` |

Keep controllers thin. A controller function should read like: validate input → call one service → serialize → return.

## 4. Naming

| Thing | Convention | Example |
|---|---|---|
| Python modules | `snake_case.py`, with layer suffix outside `models/` | `job_service.py`, `job_schema.py`, `job_controller.py` |
| Python classes | `PascalCase` | `CandidateProfile`, `JobSchema` |
| Functions / variables | `snake_case` | `check_eligibility()` |
| Blueprints | `<resource>_bp` | `job_bp`, `admin_approval_bp` |
| DB tables | plural `snake_case` | `candidate_profiles` |
| API routes | `/api/<plural-noun>`, kebab-case, no verbs | `GET /api/jobs/<id>/requirements` |
| React components / pages | `PascalCase.jsx`, pages end in `Page` | `JobCard.jsx`, `JobSearchPage.jsx` |
| Hooks | `useCamelCase.js` | `useAuth.js` |
| Other JS files | `camelCase.js` | `api/jobs.js`, `utils/formatDate.js` |
| Frontend tests | next to the file, `.test.jsx` | `JobCard.test.jsx` |
| Styling | Tailwind utilities only; brand colour names from `@theme` | `text-heritage`, `bg-cream` |
| Page components | default export (lazy loading); everything else named exports | `export default function ProfilePage()` |
| Migrations | message starts with task ID | `flask db migrate -m "T-013 add jobs tables"` |

Use the same domain words everywhere: `job`, `candidate_profile`, `application`, `snapshot`, `requirement`, `approval`, `status_event`, matching the data model in the flow doc. Don't mix synonyms (`vacancy`/`post`/`job`, `user`/`applicant`/`candidate`).

## 5. Repo hygiene rules

### Creating files and folders
1. **Every new file belongs to a task.** Don't create files "for later", and don't create empty stub modules.
2. **Use the existing structure.** New top-level folders, or new folders directly under `backend/app/` or `frontend/src/`, need a task and agreement from the team. Add them to this file in the same PR.
3. **Search before you create.** Look for an existing helper, component or service before writing a new one. No `utils2.py`, `helpers_new.js` or near-duplicates.
4. **One responsibility per file.** Split a file when it passes ~300 lines or starts doing two unrelated things.
5. **Remove `.gitkeep`** from a folder once it has a real file in it.
6. **No `__init__.py` outside `backend/`.** Every folder under `backend/app/` is a package and needs one.

### Keeping code clean
7. **Delete dead code.** Don't comment it out; Git remembers it.
8. **No debug leftovers:** `print()`, `console.log`, `breakpoint()`, `debugger`, temporary test routes.
9. **No hard-coded secrets, URLs, or credentials.** Use config / env vars and document new ones in `.env.example`.
10. **No real personal data** (CNICs, phone numbers, documents) in code, tests, fixtures, logs or commits. Use obviously fake values like `00000-0000000-0`.
11. **Formatters and linters must pass** (Ruff + Black, ESLint + Prettier) before pushing.
12. **Tests live with the layer they test** (backend) or next to the component (frontend).

### What never gets committed
13. `.env` files, `node_modules/`, virtualenvs, `__pycache__/`, build output (`dist/`, `build/`), coverage reports, uploaded files, IDE settings, OS files. `.gitignore` covers these; if you create a new kind of generated file, add it there.
14. Scratch files, experiments, notebooks, exported data dumps. Keep them outside the repo.
15. Large binaries (> 1 MB) without team agreement.

### Dependencies
16. Pin versions: `requirements.txt` with exact versions; always commit `package-lock.json`.
17. Every new dependency is noted in your work log with a one-line reason. Prefer the standard library or an existing dependency.

### Migrations
18. Generate migrations only with `flask db migrate`, review the generated file, and commit it with the model change. Autogenerate misses sequences, and CHECK constraints that can evaluate to NULL pass silently. Test new constraints. Run `flask db check` to confirm models and migrations match.
19. Never edit a migration that's already on `main`; write a new one.

### Before every commit
20. Run `git status` and read the list. Stage only files that belong to your task.
21. Confirm new files sit where §2 says they should, and follow the naming rules in §4.
